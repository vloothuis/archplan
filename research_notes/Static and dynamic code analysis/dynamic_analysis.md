## 1. Runtime tracing and instrumentation mechanisms per language, and their overhead

### Takeaway
Every target language now has a low-overhead, first-party event API that can record call entry and exit: `sys.monitoring` in Python 3.12+, `diagnostics_channel` and the V8 inspector in Node, `runtime/trace` in Go (1 to 2% CPU since Go 1.21), and trace sessions in OTP 27+. Published overhead numbers exist for Go, Node context tracking, Java monitoring agents and native sanitizers, but there is no authoritative published figure for Python `sys.settrace` versus `sys.monitoring`; the maintainers describe the gain only qualitatively.

### Cited Findings

**Python**
- PEP 669 added `sys.monitoring` in Python 3.12. Its stated aim is to let profilers, debuggers and coverage tools avoid the "punitive overhead" of `sys.settrace`. The PEP expects code under a debugger on 3.12 to outperform code without a debugger on 3.11, and says profiling "will still slow down execution, but by much less than in 3.11". A python-dev reviewer noted that the PEP contains no timing benchmarks for coverage, profiling or tracing. Sources: [PEP 669](https://peps.python.org/pep-0669/), [python-dev thread](https://mail.python.org/archives/list/python-dev@python.org/thread/VNSD4TSAM2BM64FJNIQPAOPNEGNX4MDX)
- The key mechanism is per-location disabling: a callback can return `DISABLE` so the event never fires again for that code location. The docs say a program can run under a debugger "with no overhead" if all monitoring except a few breakpoints is disabled. Source: [sys.monitoring docs](https://docs.python.org/3/library/sys.monitoring.html)
- **[memory]** `sys.monitoring` offers six tool ids (debugger 0, coverage 1, profiler 2, optimizer 5 are predefined), global events and per-code-object "local" events, with event types including `PY_START`, `PY_RETURN`, `PY_YIELD`, `PY_RESUME`, `CALL`, `C_RETURN`, `RAISE`, `LINE`, `BRANCH`. Source: [sys.monitoring docs](https://docs.python.org/3/library/sys.monitoring.html)
- Ned Batchelder (coverage.py maintainer) explains why `settrace` is slow for coverage: Python calls the trace function for every executed line even after the line is recorded, whereas `sys.monitoring` "lets me disable an event once it's fired, so after the first ping there's no overhead". He gives no numbers ("If all goes well, it should be faster"). Source: [Faster branch coverage measurement, March 2025](https://nedbatchelder.com/blog/202503/faster_branch_coverage_measurement)
- coverage.py history of the `sysmon` core: experimental in 7.4.0 (Dec 2023) for Python 3.12+ ("should be faster for line coverage, but not for branch coverage"); branch coverage with sysmon from 7.7.0 on Python 3.14; default core on Python 3.14+ since 7.9.1 (June 2025). Limits: plugins and dynamic contexts are not supported with sysmon; 7.15.3 (Aug 2026) added a warning because contexts were silently dropped; sysmon bugs with phantom or missing branches were still being fixed in 7.17.0 and 7.17.1 (Oct and Nov 2026). Latest release seen: 7.17.3 (2026-11-11). Source: [coverage.py changelog](https://coverage.readthedocs.io/en/latest/changes.html)
- A coverage.py issue reports that the settrace-based path became markedly slower on Python 3.12 when PEP 669 is not used, and that `COVERAGE_CORE=sysmon` fixed it for several users. Source: [coveragepy issue 1665](https://github.com/nedbat/coveragepy/issues/1665)
- coverage.py "dynamic contexts" record which test executed each line (who-tests-what). They need the settrace-based core. Sources: [coverage.py contexts docs](https://coverage.readthedocs.io/en/latest/contexts.html) **[memory]**, [coverage.py changelog](https://coverage.readthedocs.io/en/latest/changes.html)
- VizTracer (deterministic function-entry/exit tracer with a timeline viewer) uses `sys.setprofile()` before Python 3.12 and `sys.monitoring` on 3.12+. It conflicts with other tools that use the same hooks and cannot save data when code calls `os._exit`. Its limitations page gives no overhead number. Source: [VizTracer limitations](https://viztracer.readthedocs.io/en/latest/limitations.html)
- `tprof`, a targeted profiler built on `sys.monitoring`, reported per-call overhead on a trivial function dropping from about 439 ns to 141 ns in release 1.3.0 on Python 3.13. This is the only concrete per-call `sys.monitoring` figure found. Source: [Adam Johnson, tprof 1.3.0, Aug 2026](https://adamj.eu/tech/2026/08/08/python-tprof-performance/)
- pyinstrument's benchmark puts cProfile's overhead as high as 84% on its Django template workload. Source: [pydevtools handbook, sampling vs deterministic profilers](https://pydevtools.com/handbook/explanation/sampling-vs-deterministic-profilers/). **[memory]** The same pyinstrument table lists pyinstrument at about 30% and pure-Python `profile` at about 2000%. Source: [pyinstrument docs, how it works](https://pyinstrument.readthedocs.io/en/latest/how-it-works.html)
- py-spy and Austin are out-of-process sampling profilers. They read the interpreter's memory from another process, so the target pays no instrumentation cost. They give statistical stacks, not complete call sequences. Sources: [pydevtools handbook](https://pydevtools.com/handbook/explanation/sampling-vs-deterministic-profilers/), [py-spy](https://github.com/benfred/py-spy), [Austin](https://github.com/P403n1x87/austin)
- Python 3.15 ships a standard-library sampling profiler. PEP 799 (accepted) creates a `profiling` package with `profiling.tracing` (the former cProfile) and `profiling.sampling` ("Tachyon"), which attaches to a live process by pid. The `profile` module is deprecated in 3.15 and scheduled for removal in 3.17. A third-party blog reports a 1 kHz default sampling rate; this was not confirmed in official docs. Sources: [PEP 799](https://peps.python.org/pep-0799/), [profiling.sampling docs](https://docs.python.org/3.15/library/profiling.sampling.html), [Real Python on the 3.15 sampler](https://realpython.com/python315-sampling-profiler/)
- **[memory]** PEP 768 (Python 3.14) adds `sys.remote_exec`, a safe way to inject a script into a running interpreter, which makes attach-on-demand tracing possible without starting the process under a tracer. Source: [PEP 768](https://peps.python.org/pep-0768/)
- **[memory]** PEP 578 (Python 3.8) audit hooks (`sys.addaudithook`) fire on security-relevant runtime events such as `open`, `import`, `exec`, `socket.connect`, `subprocess.Popen`. Hooks cannot be removed once added. They observe side effects, not call structure. Source: [PEP 578](https://peps.python.org/pep-0578/)
- Scalene (OSDI 2023 paper) is a sampling CPU, memory and GPU profiler whose paper compares the overhead and accuracy of Python profilers. Source: [Berger et al., OSDI 2023](https://usenix.org/system/files/osdi23-berger.pdf)

**Node.js and TypeScript**
- A Platformatic benchmark on Node 24.4.1 with Fastify: baseline about 57,301 req/s; with `AsyncLocalStorage` about 53,450 req/s (about 7% loss); with selective OpenTelemetry instrumentation about 35.9% of baseline; with full OpenTelemetry auto-instrumentation about 18.6% of baseline. Node 24 was faster than Node 22 for context tracking. This is one vendor's benchmark on one workload. Source: [Platformatic, The Hidden Cost of Context](https://blog.platformatic.dev/the-hidden-cost-of-context)
- Node 24 switched `AsyncLocalStorage` to the `AsyncContextFrame` implementation by default. A New Relic agent issue reports memory leaks with `enterWith()` under the new default and notes that Node docs suggest `TracingChannel` as the modern replacement. Source: [node-newrelic issue 3870](https://github.gg22.workers.dev/newrelic/node-newrelic/issues/3870)
- **[memory]** `diagnostics_channel` and its `TracingChannel` give named publish/subscribe channels with start, end, asyncStart, asyncEnd and error events, at near-zero cost when no subscriber exists. Libraries must publish to channels, so it does not trace arbitrary functions. Source: [Node diagnostics_channel docs](https://nodejs.org/api/diagnostics_channel.html)
- **[memory]** The `async_hooks` low-level API is marked experimental and the docs advise migrating away from it to `AsyncLocalStorage`. Source: [Node async_hooks docs](https://nodejs.org/api/async_hooks.html)
- **[memory]** V8 has built-in coverage. "Best-effort" coverage has no overhead but loses counts for garbage-collected functions; "precise" coverage (inspector `Profiler.startPreciseCoverage`) supports call counts and block granularity. Node exposes it through `NODE_V8_COVERAGE`, which `c8` and the built-in test runner's `--experimental-test-coverage` use. The inspector `Profiler` domain also gives sampled CPU profiles (`--cpu-prof`). There is no first-party API that emits every function entry and exit; full call tracing needs source or loader instrumentation. Sources: [V8 blog, JavaScript code coverage](https://v8.dev/blog/javascript-code-coverage), [Node CLI docs](https://nodejs.org/api/cli.html)

**Go**
- Before Go 1.21 execution tracing cost "somewhere between 10 to 20% CPU for many applications". After the 1.21 optimisations it is "1 to 2% for many applications". Go 1.22 made traces splittable and scalable. An experimental reader API lives in `golang.org/x/exp/trace`. Source: [Go blog, More powerful Go execution traces, 2024](https://go.dev/blog/execution-traces-2024)
- Go 1.25 ships `trace.FlightRecorder`, which keeps the last few seconds of trace in memory and writes a snapshot on demand. Only one flight recorder may be active. Sources: [Go blog, Flight Recorder in Go 1.25](https://go.dev/blog/flight-recorder), [runtime/trace docs](https://pkg.go.dev/runtime/trace)
- **[memory]** `runtime/trace` records goroutine scheduling, syscalls, GC and user-defined tasks and regions, not every function call. `pprof` is a sampling profiler (default 100 Hz for CPU). Go 1.20 added `go build -cover` so coverage can be collected from integration-test binaries, not only from `go test`. Sources: [runtime/trace docs](https://pkg.go.dev/runtime/trace), [runtime/pprof docs](https://pkg.go.dev/runtime/pprof), [Go coverage for integration tests](https://go.dev/doc/build-cover)
- eBPF uprobes work on Go binaries, but return probes (uretprobes) crash Go programs when the runtime grows or shrinks a goroutine stack, because the probe rewrites the return address. The standard workaround is to put plain uprobes on every `RET` instruction. Tools must also track register calling conventions and per-version struct offsets. Sources: [bcc issue 1320](https://github.com/iovisor/bcc/issues/1320), [SREcon23 APAC slides](https://www.usenix.net/system/files/srecon23apac_slides-liang_zhichuan.pdf)
- OpenTelemetry now documents two zero-code routes for Go: runtime attachment with OpenTelemetry eBPF Instrumentation (OBI, the former Grafana Beyla) and compile-time weaving. OBI falls back to kprobe and tracepoint network-level data when uprobe injection fails. Sources: [OTel, choosing zero-code instrumentation for Go](https://opentelemetry.io/docs/zero-code/go/), [OBI docs](https://opentelemetry.io/docs/zero-code/obi/), [OBI troubleshooting](https://opentelemetry.io/docs/zero-code/obi/troubleshooting/), [Sematext comparison of OBI and Otelc](https://sematext.com/blog/zero-code-opentelemetry-for-go-obi-vs-otelc/)
- Go race detector: "memory usage may increase by 5-10x and execution time by 2-20x". It "only finds races that happen at runtime, so it can't find races in code paths that are not executed". Source: [Go race detector article](https://go.dev/doc/articles/race_detector)

**Elixir and the BEAM**
- OTP 27.0 added the `trace` module with trace sessions: each session is an isolated tracer, several can run at once without interfering, and destroying a session removes all its settings. The older `erlang:trace/3` shared one global tracer state. The docs recommend `dbg` for debugging and `tprof` for profiling. Source: [OTP trace module docs](https://www.erlang.org/doc/apps/kernel/trace.html)
- Tracer callbacks (`erl_tracer`) run in the context of the process that triggered the trace probe, so trace cost lands on the traced process. Source: [erl_tracer docs](https://www.erlang.org/doc/apps/erts/erl_tracer.html)
- `recon_trace` is designed for safe call tracing on production nodes, with rate and count limits. It targets the same safety level as `redbug`. Source: [recon_trace docs](https://hexdocs.pm/recon/recon_trace.html)
- **[memory]** BEAM call tracing can match on module, function and arity with match specifications, can include caller, arguments, return values and timestamps, and needs no recompilation. `:telemetry` is an opt-in event library: code must emit events, so it shows only what libraries chose to expose (Phoenix, Ecto, Oban and others do). OTP 27 also added native line-coverage support in the JIT, which is cheaper than the classic `cover` tool that recompiles modules with counters. Sources: [Erlang tracing guide](https://www.erlang.org/doc/apps/erts/tracing), [telemetry docs](https://hexdocs.pm/telemetry), [code module, native coverage support](https://www.erlang.org/doc/apps/kernel/code.html)

**Cross-language**
- MooBench results for Java monitoring frameworks: Kieker's per-invocation overhead fell from 4.77 µs to 0.39 µs after optimisation (2023 paper); other configurations measured Kieker at about 5.5 to 7.1 µs per call. A 2024 study found that OpenTelemetry's Java agent has significantly higher overhead than Kieker, not caused by its ByteBuddy instrumentation, and that source-code instrumentation had the lowest overhead. A 2026 paper extends MooBench to Elastic APM, inspectIT, Kieker, OpenTelemetry, Pinpoint, Scouter and SkyWalking. Sources: [Towards Solving the Challenge of Minimal Overhead Monitoring, 2023](https://arxiv.org/pdf/2304.05688v1), [Overhead Comparison of Instrumentation Frameworks, ICPE 2024](https://research.spec.org/icpe_proceedings/2024/companion/p249.pdf), [Cloudprofiler with MooBench](https://arxiv.org/pdf/2411.17413), [Benchmarking the Overhead of Distributed Tracing Agents, 2026](https://eprints.lancs.ac.uk/id/eprint/237563/)
- Sanitizer overheads from the authors' slides: AddressSanitizer about 2x CPU and 1.5 to 3x memory, against 20x or more for Valgrind; MemorySanitizer about 3x (about 6x with origin tracking; later slides say 2.5x and 4x); ThreadSanitizer 4 to 10x CPU and 5 to 8x RAM. Sources: [Serebryany, LLVM dev meeting 2011](https://LLVM.org/devmtg/2011-11/Serebryany_FindingRacesMemoryErrors.pdf), [Serebryany, LLVM dev meeting 2012](https://LLVM.org/devmtg/2012-11/Serebryany_TSan-MSan.pdf). **[memory]** Current Clang docs state typical slowdowns of 2x (ASan), 3x (MSan) and 5 to 15x with 5 to 10x memory (TSan); the ASan paper (USENIX ATC 2012) reports 73% average slowdown. Sources: [Clang ASan docs](https://clang.llvm.org/docs/AddressSanitizer.html), [Clang TSan docs](https://clang.llvm.org/docs/ThreadSanitizer.html), [Clang MSan docs](https://clang.llvm.org/docs/MemorySanitizer.html), [ASan paper](https://www.usenix.org/conference/atc12/technical-sessions/presentation/serebryany)
- **[memory]** OpenTelemetry auto-instrumentation in Python and Node works by monkey-patching known libraries (HTTP servers and clients, database drivers, queues). It produces spans at library boundaries, not application function calls. Sources: [OTel Python zero-code](https://opentelemetry.io/docs/zero-code/python/), [OTel JS zero-code](https://opentelemetry.io/docs/zero-code/js/)

### Inferences
- archplan's Python tracer should move to `sys.monitoring` on 3.12+ (keep the `settrace`/`setprofile` path for 3.10 and 3.11). Subscribing only to `PY_START`, `PY_RETURN`, `PY_UNWIND`, `PY_YIELD` and `PY_RESUME` gives call sequences without per-line cost. Returning `DISABLE` for code objects outside the repository (stdlib, site-packages) removes their cost after the first hit. Call-sequence recording cannot disable in-repo events the way coverage does, because order and repetition matter; a per-edge repetition cap achieves a similar effect.
- Tool-id contention is real: coverage.py had to stop assuming its id was free (7.14.2). A tracer that runs next to coverage.py should pick a free tool id and tolerate other tools. VizTracer documents the same conflict class.
- For TypeScript there is no cheap built-in call-entry hook. Realistic options are (a) V8 precise coverage with call counts for "was this function executed, how often", which gives node-level but not edge-level facts, (b) a loader or transpile-time wrapper as AppMap's Node agent does, or (c) `AsyncLocalStorage` (about 7% cost) to keep the per-request call stack across awaits.
- For Go, `runtime/trace` user regions and tasks are cheap but need manual annotation. Complete call sequences need compile-time rewriting (`-toolexec` style, as OTel's compile-time instrumentation does) or eBPF with the RET-uprobe workaround, which is Linux-only and needs privileges. Coverage counters from `go build -cover` are the zero-dependency fallback and confirm which statically predicted functions ran.
- The BEAM is the easiest target: `trace:session_create` plus `call` and `return_to` or `return_trace` flags limited to the project's modules gives exact cross-process call sequences from `mix test` without touching the code. Trace sessions remove the old risk of clashing with another tracer.
- Sampling profilers (py-spy, Austin, Tachyon, pprof) cannot give call order, but their stacks confirm caller-callee edges at near-zero cost. They suit "confirm a static edge on a production-like run".

### Gaps
- No authoritative benchmark was found that quantifies `sys.settrace` or `sys.setprofile` slowdown against `sys.monitoring` for call tracing. PEP 669 and coverage.py give only qualitative claims. A PyCon US 2024 talk title claims a debugger can be made "100x faster"; the measured result was not retrieved.
- No published overhead figures were found for VizTracer, Austin, py-spy (as a percentage), BEAM call tracing, `recon_trace`, Erlang `cover`, V8 precise coverage, `diagnostics_channel`, Delve, Frida, DTrace, Pin or DynamoRIO in this session. Valgrind's figure comes only via the ASan authors' comparison.
- The "1 to 2% versus 10 to 20%" figure sometimes attached to the Go flight recorder is the general tracing figure from the 2024 blog post, not a separate flight-recorder measurement.
- Whether cProfile itself uses `sys.monitoring` in current CPython was not confirmed; one source still describes it as built on `PyEval_SetProfile`.

## 2. Dynamic call-graph and architecture recovery

### Takeaway
Dynamic call graphs are precise but only as complete as the test inputs, while static call graphs for dynamic languages miss 12 to 30% of real edges; the best published results come from feeding runtime observations into the static analysis. AppMap is the closest existing product to archplan's tracer (per-test recordings rendered as sequence and dependency diagrams), and Kieker/ExplorViz are the main research line for trace-based architecture views.

### Cited Findings
- AppMap is an open-source runtime analysis tool for Ruby, Java, Python and Node.js. The Python agent hooks module import, finds function definitions and wraps each configured function so that a call adds an event to the current recording. Recording modes: per test case (pytest plugin, unittest), per HTTP request, remote (start/stop), whole process, and an explicit `appmap.Recording` context manager. It records function calls, parameters (rendered with `repr`), return values, exceptions, HTTP server and client requests and SQL. Scope is set in `appmap.yml` by package path with `exclude` and a `shallow` option that records only entry calls into a package; dependency packages default to shallow. The current agent supports Python 3.11 to 3.15. A 3.0.1 wheel was published on PyPI in July 2026. Sources: [appmap-python reference](https://appmap.io/docs/reference/appmap-python.html), [appmap on PyPI](https://pypi.org/project/appmap)
- AppMap files are JSON with an `events` array plus metadata and a code-structure index; the CLI (`@appland/appmap` on npm) converts them to sequence diagrams, including PlantUML output via `appmap sequence-diagram`. Sources: [appmap-python reference](https://appmap.io/docs/reference/appmap-python.html), [AppMap sequence diagram post](https://dev.to/appmap/auto-magically-generate-sequence-diagrams-of-your-codes-runtime-behavior-597a)
- ExplorViz is an open-source research tool that gives live trace visualisation of software landscapes with a 3D "software city" metaphor. It has moved from Kieker-specific monitoring to OpenTelemetry. Hansen and Hasselbring (2024) note that purely distributed (service-boundary) OpenTelemetry instrumentation is not enough for ExplorViz, because the view needs internal behaviour and structure. A companion paper describes exporting Kieker records to OpenTelemetry. Sources: [ExplorViz about](https://explorviz.uni-kiel.de/1-about/), [Instrumentation of Software Systems with OpenTelemetry for Software Visualization](https://arxiv.org/abs/2411.12380v1), [Interoperability from Kieker to OpenTelemetry](https://arxiv.org/html/2411.07982v1)
- Trace reduction: Cornelissen, Moonen and Zaidman assessed four types of reduction (summarisation, metrics-based filtering, language-based filtering, ad hoc) on seven large traces. Hamou-Lhadj and Lethbridge proposed trace summarisation and utility-function filtering and measured compression on 12 traces of WEKA. Grammar-based compression (Sequitur) and LZ-family compression are the common lossless methods. Sources: [An Assessment Methodology for Trace Reduction Techniques](https://repository.tudelft.nl/record/uuid:981f0f26-8867-4331-ad0a-82428c2ca98c), [Hamou-Lhadj PhD thesis](https://ruor.uottawa.ca/items/c2bb591b-07ac-4fb5-9fec-4b1aa340de9d), [Hamou-Lhadj and Lethbridge, VISSOFT 2003](https://webhome.cs.uvic.ca/~mstorey/vissoft2003/submissions/HamouLhadjReducingComplexity.pdf), [Burtscher et al. on VPC trace compression](https://userweb.cs.txstate.edu/~mb92/papers/ieee05.pdf)
- **[memory]** The standard survey is Cornelissen et al., "A Systematic Survey of Program Comprehension through Dynamic Analysis" (IEEE TSE 2009), which classifies 176 articles. Source: [DOI 10.1109/TSE.2009.28](https://doi.org/10.1109/TSE.2009.28)
- Python static versus dynamic: PyCG (ICSE 2021) reports about 99.2% precision and about 69.9% recall on its own benchmarks. DyPyBench (50 projects, about 681k lines, about 30k tests, integrated with the DynaPyt framework) compared PyCG with dynamic call graphs; method calls on built-in types account for 59% of callees missing from the static graph, `super().method()` calls were also missing, and for some projects the dynamic graph was faster to produce than the static one. Sources: [PyCG paper](https://arxiv.org/pdf/2103.00587), [DyPyBench](https://arxiv.org/abs/2403.00539)
- An evaluation of Python call-graph frameworks found that none produced a sound graph and that static graphs contained many spurious edges. NoCFG compared static graphs with dynamic ones built with `pycallgraph`, using project tests as entry points. Sources: [Qualitative and Quantitative Analysis of Callgraph Algorithms for Python](https://ris.uni-paderborn.de/record/23388), [NoCFG](https://arxiv.org/pdf/2105.03099)
- Java: Sui et al. (ICSE 2020) measured static call-graph recall against a dynamic oracle on 31 real programs. Median recall was 0.884, rising to 0.935 with the best support for dynamic features at a heavy performance cost. The main unsoundness sources were objects created or accessed through native methods and JVM-initiated calls, not reflection. "Total Recall?" (ISSTA 2024) builds dynamic baselines with manual extension and coverage-guided fuzzing because test suites alone under-cover. Sources: [Sui et al., ICSE 2020](https://2020.icse-conferences.org/details/icse-2020-papers/47/On-the-Recall-of-Static-Call-Graph-Construction-in-Practice), [Total Recall?, ISSTA 2024](https://unpaywall.org/10.1145%2F3650212.3652114)
- JavaScript hybrid: "Reducing Static Analysis Unsoundness with Approximate Interpretation" (Laursen, Xu, Møller, PLDI 2024) runs a fully automatic dynamic pre-analysis that produces hints for the static analysis. On 36 projects with dynamic call graphs, recall rose from 75.9% to 88.1% with negligible precision loss; the wider evaluation covered 141 Node.js applications and libraries. Chakraborty et al. (ECOOP 2022) found dynamic property accesses to be the most common root cause of missed edges. Sources: [Approximate interpretation, PLDI 2024](https://cs.au.dk/~amoeller/papers/approx), [Chakraborty et al., ECOOP 2022](https://drops.dagstuhl.de/opus/volltexte/2022/16231/)
- A 2026 arXiv paper (CPyGraph) analyses native CPython bytecode version-aware for static call graphs, which shows the Python static call-graph line is still active. Source: [CPyGraph](https://arxiv.org/pdf/2609.25083)

### Inferences
- The numbers give archplan a defensible framing: static edges are a superset-with-holes (precision high, recall about 70 to 88% in dynamic languages), dynamic edges are exact but coverage-bounded. A merged model should label each edge `static-only`, `dynamic-only` or `both`. `dynamic-only` edges locate static-analysis blind spots (dynamic dispatch, built-in methods, `super()`, reflection, dynamic property access). `static-only` edges on covered callers are candidates for dead or mis-resolved edges.
- The PLDI 2024 result suggests the more valuable direction is dynamic to static: use observed receiver types and callees as hints to resolve static call sites, instead of only overlaying two graphs.
- AppMap's design choices worth imitating: one recording per test case named after the test; package-level scoping with `shallow` entry-only capture for dependencies; HTTP and SQL events as first-class leaf events so sequences end at system boundaries; a context-manager API for ad hoc recording.
- Hansen and Hasselbring's finding matters for any plan to rely on OpenTelemetry: default auto-instrumentation gives service and library boundaries only. Component-level architecture recovery needs in-process function spans, which archplan's own tracer already provides.
- Trace reduction for sequence diagrams maps to four cheap steps from the literature: filter by scope (language-based: drop getters, constructors, stdlib), cap or collapse repetitions (loops become "xN"), depth-limit by component boundary, and deduplicate identical subtrees by hashing. A per-callee fan-in metric (the "utility function" idea) removes helper noise.

### Gaps
- No source found for AppMap overhead figures, or for the current state of AppMap's Node agent and company in 2026.
- DyPyBench's absolute edge counts and overlap percentages were not extracted (PDF was unreadable through the fetch tool).
- No peer-reviewed tool was found that generates component-level sequence diagrams directly from OpenTelemetry traces, and nothing verified on Jaeger or Tempo service-graph algorithms in this session.
- No Go or Elixir study comparing static and dynamic call graphs was found.
- PyCG's maintenance status (believed archived) was not verified.

## 3. Test-adequacy techniques

### Takeaway
Coverage is a weak-to-moderate predictor of fault detection once test-suite size is controlled; mutant detection predicts real-fault detection better than statement coverage, but that correlation is also contested. The strongest industrial evidence is behavioural: at Google, surfacing a few filtered mutants in code review made developers write more and better tests.

### Cited Findings
- Inozemtseva and Holmes (ICSE 2014): after controlling for suite size, the correlation between coverage and effectiveness is low to moderate, so coverage is not a safe quality target on its own. Sources: [paper](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf), [review](https://neverworkintheory.org/2021/09/24/coverage-is-not-strongly-correlated-with-test-suite-effectiveness.html)
- Just et al. (FSE 2014): mutant detection correlates with real-fault detection independently of coverage, and more strongly than statement coverage does. Source: [paper](https://homes.cs.washington.edu/%7Emernst/pubs/mutation-effectiveness-fse2014.pdf)
- Papadakis et al. (ICSE 2018): correlations between mutation score and real-fault detection are weak when suite size is controlled, yet achieving higher mutation scores still improves fault detection significantly. Source: [IEEE record](https://ieeexplore.ieee.org/document/8453121)
- Chen et al. (ASE 2020) argue that suite size is neither a confounder nor a variable to manipulate, propose "probabilistic coupling", and compare coverage-adequate and mutation-adequate test sets on 2,311 real faults from Defects4J. Sources: [paper](https://homes.cs.washington.edu/~mernst/pubs/test-set-size-ase2020.pdf), [companion: Mutants and Real Faults Revisited](https://homes.cs.washington.edu/~rjust/publ/mutants_faults_revisited_ase_2020.pdf)
- A large Java study found only a weak relation between statement coverage or mutation score and later bug fixes. Source: [DOI 10.1145/2950290.2950324](https://www.doi.org/10.1145/2950290.2950324)
- Google, "Practical Mutation Testing at Scale" (TSE 2021): developers first judged 85% of reported mutants unproductive. The deployed system mutates only changed lines during code review, suppresses mutants in "arid" code and picks operators by historical performance. Evaluation: almost 17 million mutants, 760,000 changes, 2 million mutants surfaced in review; setting of more than 24,000 developers on more than 1,000 projects. Sources: [arXiv 2102.11378](https://arxiv.org/abs/2102.11378), [Google Research page](https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/)
- Google, "Does mutation testing improve testing practices?" (ICSE 2021): on about 15 million mutants, developers exposed to mutants wrote more tests and left fewer surviving mutants over time; mutants were coupled with real high-priority faults in past fixes. Source: [arXiv 2103.07189](https://emergentmind.com/papers/2103.07189)
- Tools and status: cosmic-ray (Python) is maintained, release 8.4.6 dated 2026-04-02. mutmut is the common Python choice in 2026 guides. Stryker is the standard for JavaScript and TypeScript. ThoughtWorks' radar entry on mutation testing (updated November 2026) names Stryker, Pitest and cargo-mutants. Muzak (Elixir) had its last push in December 2022 and its author said in 2022 it was less supported than he would like; treat as unmaintained. Sources: [cosmic-ray summary](https://dev.co/testing/open-source/cosmic-ray), [ThoughtWorks radar](https://www.thoughtworks.com/radar/techniques/mutation-testing), [Muzak repo](https://github.com/tenmoves/muzak), [Elixir Forum thread](https://forum.elixirforum.com/t/mutation-testing-on-elixir-1-14/51926)
- **[memory]** Go: `go-mutesting` (zimmski) is unmaintained; forks and `gremlins` are the active options. PIT is the Java reference tool. Sources: [go-mutesting](https://github.com/zimmski/go-mutesting), [gremlins](https://github.com/go-gremlins/gremlins), [PIT](https://pitest.org)
- Property-based testing: Ravi and Coblenz (OOPSLA 2025) studied 426 Python programs using Hypothesis and ran mutation testing on 40 projects. Each property-based test killed on average about 50 times as many mutants as an average unit test, and 76% of mutants were found within the first 20 generated inputs. Sources: [OOPSLA 2025 listing](https://2025.splashcon.org/details/OOPSLA/102), [arXiv 2510.09907](https://arxiv.org/html/2510.09907v1)
- **[memory]** Property-based libraries per target language: Hypothesis (Python), fast-check (TypeScript), `rapid` and the built-in `testing/quick` (Go), StreamData and PropCheck (Elixir). Sources: [Hypothesis](https://hypothesis.readthedocs.io), [fast-check](https://fast-check.dev), [rapid](https://github.com/flyingmutant/rapid), [StreamData](https://github.com/whatyouhide/stream_data), [PropCheck](https://github.com/alfert/propcheck)
- Flaky tests at Google (2016): about 1.5% of all test runs reported a flaky result, almost 16% of tests showed some flakiness, about 84% of pass-to-fail transitions in post-submit CI involved a flaky test, and flaky reruns consumed 2 to 16% of CI compute. Source: [Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- Flaky tests in Python (Gruber et al., ICST 2021): 22,352 PyPI projects, 876,186 tests, 7,571 flaky. Causes: order dependency 59%, test infrastructure 28%, remainder mostly network and randomness. About 170 reruns are needed for 95% confidence that a passing test is not flaky. Source: [arXiv 2101.09077](https://arxiv.org/abs/2101.09077)

### Inferences
- For a tool like archplan, coverage is best presented as a negative signal (uncovered components and edges are unverified and untraced), not as a quality score. This matches the evidence and also bounds the trust in the dynamic part of the model.
- Google's design is the one to imitate for any mutation feature: diff-scoped, few mutants, suppression of unproductive locations. A static model helps here: mutants can be prioritised on components with high fan-in or on edges that tests execute but never assert on.
- Per-test traces enable cheap adequacy signals without mutation: functions executed only transitively (never called directly by a test), components reached by a single test, and tests whose traces are identical (redundancy).
- The Python flakiness data (59% order-dependent) suggests a low-cost dynamic check: run the suite in shuffled order and diff outcomes. Trace divergence between two runs of the same test is a direct non-determinism detector that a sequence recorder gets almost for free.
- The 76%-in-20-inputs result means property tests can run with small example budgets during tracing without losing much.

### Gaps
- mutmut 3.x details and its 2026 release state were not confirmed. Stryker's current version and incremental-mode performance numbers were not retrieved.
- The post-filtering productive-mutant rate at Google was not retrieved from the full paper.
- No verified evidence on differential or metamorphic testing effectiveness was collected in this session.
- No current (2024 to 2026) replication of coverage-versus-fault-detection for Python, TypeScript, Go or Elixir was found; the cited studies are Java-based and date from 2014 to 2020.

## 4. Security-oriented dynamic analysis

### Takeaway
Coverage-guided fuzzing has the largest published yield (OSS-Fuzz: over 13,000 vulnerabilities and 50,000 bugs across 1,000 projects by May 2025), but mainly for memory-unsafe code; for Python, TypeScript, Go and Elixir services the productive dynamic techniques are schema-driven API fuzzing, dynamic taint tracking (IAST) and replay-based authorization checks. Open-source fuzzers for Python and JavaScript are weakly maintained.

### Cited Findings
- OSS-Fuzz: "over 13,000 vulnerabilities and 50,000 bugs across 1,000 projects" as of May 2025 (10,000 and 36,000 as of August 2023). Source: [OSS-Fuzz README](https://github.com/google/oss-fuzz)
- Limits of continuous fuzzing: a GitHub Security Lab researcher found 29 new vulnerabilities in GStreamer after seven years of OSS-Fuzz enrolment and attributed the gap to low coverage, missing fuzzers and unfuzzed dependencies. Source: [news summary](https://letsdatascience.com/news/oss-fuzz-fails-to-detect-longstanding-vulnerabilities-fe2198e6) (secondary source)
- A 2026 paper studies how OSS-Fuzz results differ by programming language. Source: [arXiv 2602.05312](https://arxiv.org/pdf/2602.05312v1)
- Atheris (Google) is a coverage-guided Python fuzzer built on libFuzzer that covers pure Python and native extensions. No 2026 release or Python 3.13+ support statement was found; last repository activity seen was May 2025. Sources: [Atheris on PyPI](https://pypi.org/project/atheris), [How Atheris works](https://security.googleblog.com/2020/12/how-atheris-python-fuzzer-works.html)
- Jazzer.js: Code Intelligence states it stopped maintaining Jazzer.js as open source and points users to its commercial CI Fuzz. The JVM Jazzer was later returned to open source; no evidence that Jazzer.js was. Snyk rates the npm package's maintenance as inactive. Sources: [Jazzer.js repo](https://github.com/CodeIntelligenceTesting/jazzer.js), [Jazzer back to open source](https://code-intelligence.com/blog/jazzer-back-to-open-source), [Snyk advisor](https://snyk.io/advisor/npm-package/@jazzer.js/fuzzer)
- **[memory]** Go has had native coverage-guided fuzzing in the toolchain since Go 1.18 (`go test -fuzz`), limited to a fixed set of argument types. Source: [Go fuzzing docs](https://go.dev/doc/security/fuzz/)
- Schemathesis (property-based API fuzzing derived from OpenAPI or GraphQL schemas, built on Hypothesis): in the authors' evaluation of eight fuzzers on sixteen real web services it found 1.4 to 4.5 times more unique defects than the next-best tool on each target, was the only tool to find defects in four targets, and the only one to handle more than two thirds of services without a fatal internal error. It also checks response conformance and missing headers, not only crashes. The evaluation is by the tool's authors (2021). Source: [Deriving Semantics-Aware Fuzzers from Web API Schemas](https://arxiv.org/abs/2112.10328)
- **[memory]** RESTler (Microsoft) is a stateful REST fuzzer that infers producer-consumer dependencies between requests from the OpenAPI spec. Its security checkers test rule violations: use-after-free (a deleted resource is still accessible), resource leak, resource hierarchy (a child reachable through the wrong parent) and user namespace (a resource reachable with another user's token). The last two are automated checks for broken object-level authorization. Sources: [RESTler repo](https://github.com/microsoft/restler-fuzzer), [Checking Security Properties of Cloud Service REST APIs](https://www.microsoft.com/en-us/research/publication/checking-security-properties-of-cloud-services-rest-apis/)
- Authorization flaws: Palo Alto Unit 42 notes that broken object-level authorization (BOLA) is a logic error with no pattern for static tools and triggers no runtime error, which is why automation is hard. A 2025 journal paper converts an OpenAPI spec into a coloured Petri net and detects BOLA from event logs (Links2CPN). Sources: [Unit 42](https://unit42.paloaltonetworks.com/automated-bola-detection-and-ai/), [Links2CPN paper](https://zaguan.unizar.es/record/151286/files/texto_completo.pdf). **[memory]** The Burp extension Autorize replays each request with a lower-privileged session and flags equal responses. Source: [Autorize](https://github.com/PortSwigger/autorize)
- Dynamic taint tracking, Python: Datadog's IAST for Python (in `dd-trace-py`, enabled with `DD_IAST_ENABLED=true`) is in Preview. It rewrites code at runtime, can conflict with Numba, JAX, TorchScript and TensorFlow, and does not propagate taint through native code. 2026 release notes fix false positives from taint leaking between concurrent requests and a crash in `%`-formatting. The taint engine is native code. Sources: [Datadog IAST Python setup](https://docs.datadoghq.com/security/code_security/iast/setup/python), [dd-trace-py v4.10.9 notes](https://newreleases.io/project/github/DataDog/dd-trace-py/release/v4.10.9)
- Dynamic taint tracking, Node.js: NodeMedic (EuroS&P 2023) analysed 10,000 npm packages and found 155 vulnerabilities, 152 previously undisclosed, 108 confirmed with synthesised exploits. NodeMedic-FINE (NDSS 2025) analysed 33,011 packages with command-injection or code-execution sinks, found 2,257 potential flows and synthesised working exploits for 766 packages. Augur is a taint analysis for Node.js built on NodeProf (GraalVM), which is hard to install. A 2025 follow-up builds a triage benchmark of 1,883 packages. Sources: [NodeMedic-FINE](https://www.ndss-symposium.org/ndss-paper/nodemedic-fine-automatic-detection-and-exploit-synthesis-for-node-js-vulnerabilities/), [NodeMedic](https://ink.library.smu.edu.sg/sis_research/8094), [Augur](https://www.github.com/nuprl/augur), [Learning to Triage Taint Flows](https://arxiv.org/html/2510.20739v1)
- Symbolic and concolic execution: CrossHair executes real Python functions with symbolic proxy objects backed by the Z3 solver to find counterexamples to contracts (asserts, PEP 316 docstrings, icontract, deal). It can also diff the behaviour of two functions and serves as an optional Hypothesis backend through `hypothesis-crosshair`. Sources: [CrossHair contracts docs](https://crosshair.readthedocs.io/en/latest/contracts.html), [hypothesis-crosshair](https://pypi.org/project/hypothesis-crosshair)
- **[memory]** KLEE (OSDI 2008) reached over 90% line coverage on GNU coreutils and found 56 serious bugs; angr is the main binary symbolic-execution framework. Sources: [KLEE paper](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/cadar/cadar.pdf), [angr](https://angr.io)
- **[memory]** DAST tools: OWASP ZAP (open source, now under Checkmarx sponsorship), Burp Suite (commercial) and Nuclei (template-based scanner) probe a running application from outside without code knowledge. Sources: [ZAP](https://www.zaproxy.org/), [Nuclei](https://github.com/projectdiscovery/nuclei)
- Sanitizers and the Go race detector: see overhead figures in section 1. Sources: [Go race detector](https://go.dev/doc/articles/race_detector), [Serebryany slides](https://LLVM.org/devmtg/2012-11/Serebryany_TSan-MSan.pdf)

### Inferences
- Memory-safety fuzzing and sanitizers are of low relevance to archplan's four languages, except for Go's race detector (`go test -race`) and native extensions. In memory-safe languages fuzzers find uncaught exceptions, hangs and logic errors, so they need an oracle (properties, differential checks, schema conformance).
- The place where a static architecture model adds security value to dynamic analysis is in source and sink mapping: the model knows entry points (HTTP handlers, CLI commands, queue consumers) and sinks (SQL, subprocess, file, HTTP client). A recorded call sequence that connects an entry point to a sink without passing through a validation or authorization component is a taint-style finding without value-level taint tracking. It is weaker than IAST (no data-flow proof) but needs no native engine.
- The same idea applies to authorization: per-request traces show whether an authorization function ran before a data-access function. "Handler reached the repository layer with no call to any authorization component" is checkable on traces; a static-only check would miss decorators, middleware and dynamic dispatch. RESTler's user-namespace and resource-hierarchy rules show which replay experiments confirm such a suspicion.
- PEP 578 audit hooks give a zero-dependency way to record sink events (`open`, `subprocess.Popen`, `socket.connect`, `exec`, `import`) with the current stack during test runs, which would let archplan attach "performs file, network or process I/O" facts to components.
- Schemathesis can serve as an input generator for tracing: driving an API with schema-derived requests exercises handlers that unit tests miss, which raises trace coverage.

### Gaps
- No published overhead figures for Python or Node IAST or taint tracking were found. Vendor material makes no quantified claim.
- No verified material on RASP products, on Burp or ZAP detection rates, or on grammar-based and structure-aware fuzzing results was collected in this session.
- OSS-Fuzz has no newer official aggregate than May 2025 in the sources found. Per-language shares of OSS-Fuzz findings were not extracted.
- No fuzzing or taint tooling for Elixir was found beyond property-based testing.
- AFL++ and libFuzzer status in 2026 was not checked.

## 5. Invariant and specification mining, runtime verification, contracts and runtime type collection

### Takeaway
Runtime observation is an established way to refine static models: Daikon infers likely invariants from traces, MonkeyType and RightTyper infer types from calls, and contract libraries plus CrossHair turn stated properties into checked ones. The cost problem of full-trace type collection has been addressed by sampling (RightTyper reports about 27% overhead).

### Cited Findings
- Daikon runs a program, observes computed values and reports properties that held on all observed executions ("likely invariants"). It supports C, C++, Java and Perl and record-structured data such as CSV, and is extensible to other front ends. Original paper: Ernst et al., IEEE TSE 2001; system description 2007. Sources: [The Daikon system](https://typeset.io/papers/the-daikon-system-for-dynamic-detection-of-likely-invariants-3cl4ljbvv1), [Daikon site](https://plse.cs.washington.edu/daikon/)
- MonkeyType (Instagram) records argument and return types through `sys.setprofile` and stores them in SQLite; it requires Python 3.9+ and `libcst`. Sampling of calls exists but is off by default. The RightTyper authors describe its runtime and storage cost as substantial. No 2026 release evidence was found. Sources: [MonkeyType docs](https://monkeytype.readthedocs.io/en/stable/), [RightTyper paper](https://arxiv.org/html/2507.16051v3)
- PyAnnotate was last updated in March 2021 and appears unmaintained. Source: [RightTyper paper](https://arxiv.org/html/2507.16051v3)
- RightTyper is a sampling-based dynamic type-inference tool for Python that reports about 27% runtime overhead (paper revised March 2026). Source: [RightTyper paper](https://arxiv.org/html/2507.16051v3)
- DyPyBench used execution traces of 50 Python projects to mine API-usage specifications and set a baseline for specification mining in Python. It builds on DynaPyt, a general dynamic-analysis framework for Python with analysis hooks. Source: [DyPyBench](https://arxiv.org/abs/2403.00539)
- CrossHair checks contracts written as plain asserts, PEP 316 docstrings, icontract decorators and deal decorators; all kinds are checked by default. Source: [CrossHair contracts docs](https://crosshair.readthedocs.io/en/latest/contracts.html)
- **[memory]** icontract and deal are decorator-based design-by-contract libraries for Python that check preconditions, postconditions and invariants at run time; deal also declares allowed exceptions and side effects (`@deal.raises`, `@deal.has`). Sources: [icontract](https://github.com/Parquery/icontract), [deal](https://deal.readthedocs.io)
- **[memory]** On the BEAM, Dialyzer type specs are static, but tracing with match specifications can capture argument and return terms for chosen functions, which is the raw material for the same kind of inference. Source: [Erlang tracing guide](https://www.erlang.org/doc/apps/erts/tracing)

### Inferences
- archplan exports "types" in its model. Recording the concrete receiver class and argument and return type names at `PY_START` and `PY_RETURN`, sampled as RightTyper does, would let it (a) resolve static call sites whose receiver type is unknown, (b) flag declared-versus-observed type mismatches, and (c) list concrete implementations seen behind an abstract dependency. This is the "runtime observations refine the static model" loop with the best published support (PLDI 2024 hints result in section 2).
- Daikon-style inference over call sequences gives architecture-level invariants cheaply: "A is always called before B", "component X is never called from component Y", "function f is only called inside a transaction". Mined from passing test traces, these are candidate architecture rules that archplan's static detectors could then enforce. They are "likely" only: they hold on observed runs, and need a support threshold (number of distinct tests) and human confirmation.
- Sequence-order rules mined this way are simple runtime-verification properties. Checking them on later traces is a regression test for architecture.
- `deal`'s side-effect declarations and PEP 578 audit events can cross-check each other: declared pure, observed doing I/O.

### Gaps
- No verified information on Daikon's current maintenance state, on a Python front end for Daikon, or on successors (DIG, Dinv, SLING) was found in this session.
- No runtime-verification framework for Python, TypeScript, Go or Elixir with published adoption or overhead data was found. Coverage of this sub-topic is thin.
- DynaPyt's overhead range was not verified.
- MonkeyType's 2026 maintenance state is unknown.
- No source was found on runtime type collection for TypeScript, Go or Elixir.

## 6. Known limits of dynamic analysis

### Takeaway
Dynamic results are true only for the executions observed: every dynamic tool states this limit, flaky and order-dependent behaviour makes single runs unreliable, and the cost ranges from 1 to 2% (Go tracing) through 2 to 20x (race detection) to thousands of core-hours (fuzzing, mutation). No study was found that compares bugs found by static and dynamic techniques on Python, TypeScript, Go or Elixir.

### Cited Findings
- Coverage dependence, stated by the tools: the Go race detector "can't find races in code paths that are not executed"; Sui et al. had to treat test-derived call graphs as an under-approximate oracle; "Total Recall?" adds fuzzing because tests alone under-cover; 29 GStreamer vulnerabilities survived seven years of OSS-Fuzz because of low coverage and missing harnesses. Sources: [Go race detector](https://go.dev/doc/articles/race_detector), [Sui et al.](https://2020.icse-conferences.org/details/icse-2020-papers/47/On-the-Recall-of-Static-Call-Graph-Construction-in-Practice), [Total Recall?](https://unpaywall.org/10.1145%2F3650212.3652114), [GStreamer report summary](https://letsdatascience.com/news/oss-fuzz-fails-to-detect-longstanding-vulnerabilities-fe2198e6)
- Non-determinism: about 16% of Google's tests showed some flakiness; in Python 59% of flaky tests are order-dependent and 170 reruns are needed for 95% confidence that a test is not flaky. Sources: [Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html), [Gruber et al.](https://arxiv.org/abs/2101.09077)
- **[memory]** Fuzzing evaluations are noisy: Klees et al. (CCS 2018) showed that many fuzzing papers drew conclusions from too few trials and too short runs, and recommend multiple trials with statistical tests and 24-hour runs. Source: [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700)
- CI cost: flaky reruns alone used 2 to 16% of Google's CI compute; Google could deploy mutation testing only by cutting mutants by orders of magnitude and restricting them to changed lines; full OpenTelemetry auto-instrumentation cut Node throughput to about 19% of baseline in one benchmark; race detection costs 2 to 20x time and 5 to 10x memory. Sources: [Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html), [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378), [Platformatic](https://blog.platformatic.dev/the-hidden-cost-of-context), [Go race detector](https://go.dev/doc/articles/race_detector)
- Observer effects and tool conflicts: only one tool can own `sys.settrace` or `sys.setprofile`; VizTracer conflicts with other profilers; coverage.py's sysmon core cannot record dynamic contexts or support plugins; Datadog IAST's code rewriting conflicts with JIT-style libraries; uretprobes crash Go programs. Sources: [VizTracer limitations](https://viztracer.readthedocs.io/en/latest/limitations.html), [coverage.py changelog](https://coverage.readthedocs.io/en/latest/changes.html), [Datadog IAST Python](https://docs.datadoghq.com/security/code_security/iast/setup/python), [bcc issue 1320](https://github.com/iovisor/bcc/issues/1320)
- Native-code blind spots: taint tracking stops at compiled extensions; Python-level tracing does not see inside C extensions (only `C_RETURN`-style boundary events). Sources: [Datadog IAST Python](https://docs.datadoghq.com/security/code_security/iast/setup/python), [sys.monitoring docs](https://docs.python.org/3/library/sys.monitoring.html)
- Static side for comparison: Habib and Pradel (ASE 2018) ran three widely used Java static bug detectors on 594 real bugs from 15 projects and found that they miss the large majority of the bugs and are mostly complementary to each other; an earlier diff-based estimate of 50 to 95% detection did not check that warnings pointed at the bug. The paper leaves comparison with testing to future work. Sources: [study artefact](https://github.com/sola-da/StaticBugCheckers), [slides](https://www.sambuz.com/doc/how-many-of-all-bugs-do-we-find-a-study-of-static-bug-ppt-presentation-864150)
- Recall figures that quantify what static analysis misses and dynamic analysis recovers: Python about 70% (PyCG, own benchmark), JavaScript 75.9% rising to 88.1% with dynamic hints, Java 88.4% median. Sources: [PyCG](https://arxiv.org/pdf/2103.00587), [Approximate interpretation](https://cs.au.dk/~amoeller/papers/approx), [Sui et al.](https://2020.icse-conferences.org/details/icse-2020-papers/47/On-the-Recall-of-Static-Call-Graph-Construction-in-Practice)

### Inferences
- A merged model must carry provenance and coverage with every dynamic fact: which tests produced an edge, and what share of the component's functions was executed at all. Absence of a dynamic edge means "not observed", never "does not exist". The user's standing note that every archplan project has sequences fits this: detectors can rely on sequences existing, but must weight them by coverage.
- Because single runs are unreliable, facts derived from traces should be the union over runs, and divergence between runs should be reported as a finding (non-determinism), not silently merged.
- The cost profile suggests tiers: always-on cheap observation in the normal test run (call sequences with scope filtering, coverage); opt-in expensive runs (race detector, mutation on diff, API fuzzing) on a schedule or on changed components selected through the static model.
- The static and dynamic evidence is complementary in a specific way that a report can state: static tools miss most real bugs and 12 to 30% of call edges, dynamic tools miss everything on unexecuted paths. Neither figure comes from a head-to-head study in the four target languages.

### Gaps
- No peer-reviewed head-to-head study of bugs found by static versus dynamic techniques for Python, TypeScript, Go or Elixir was found. The Java study covers static detectors only.
- No published data on the CI cost of trace recording (time or storage per test) for AppMap, VizTracer or similar tools was found.
- Evidence on Elixir-specific limits (for example message-passing non-determinism in traces) was not found.
